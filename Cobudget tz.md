# Технічне завдання проєкту CoBudget

**Дисципліна:** Сучасні технології веб-розробки
**Тип роботи:** Індивідуальне семестрове завдання
**Технологічний стек:** Python, FastAPI, SQLAlchemy, PostgreSQL/SQLite, HTML, CSS (Tailwind), JavaScript

---

## AC-01. Опис та постановка задачі

### Назва проєкту

CoBudget

### Предметна область

Веб-застосунок для обліку особистих і спільних фінансів — управління доходами, витратами та бюджетами за категоріями.

### Проблема

Користувачі, що ведуть спільний бюджет (сім'я, співмешканці), не мають зручного інструменту для одночасного обліку витрат кількома особами з контролем лімітів за категоріями. Запрошення до спільного бюджету зазвичай ускладнене (ручне узгодження через сторонні канали, окремі непов'язані акаунти), а перевищення бюджету виявляється постфактум.

### Цільова аудиторія

- окремі користувачі, яким потрібен облік особистих фінансів;
- групи користувачів (сім'я, пара, співмешканці), яким потрібен спільний бюджет із розподілом прав доступу.

### Призначення системи

Система дозволяє користувачу створювати особисті або спільні бюджети, запрошувати учасників за посиланням-запрошенням, вести облік транзакцій за категоріями з установленими лімітами та відстежувати стан бюджету в реальному часі з попередженням про перевищення ліміту.

### Основні сценарії використання

1. Реєстрація та автентифікація користувача в системі.
2. Створення бюджету користувачем, який автоматично отримує роль власника (owner).
3. Генерація власником посилання-запрошення для залучення учасників до бюджету.
4. Приєднання нового користувача до бюджету за посиланням-запрошенням із присвоєнням ролі учасника (member).
5. Створення власником категорій доходів/витрат із встановленням лімітів.
6. Додавання учасником транзакції (доходу або витрати) в межах доступного йому бюджету.
7. Автоматичний перерахунок системою залишку за категорією та бюджетом у цілому; позначення категорії як такої, що перевищила ліміт.
8. Перегляд, редагування та видалення транзакцій користувачем (власних або всіх — залежно від ролі); пошук, фільтрація та сортування транзакцій за датою, категорією, сумою, автором.
9. Керування власником учасниками бюджету: перегляд списку, видалення учасника, зміна ролі.

### Перелік ключових функцій

- реєстрація та автентифікація (JWT);
- створення, редагування та видалення бюджетів;
- генерація та обробка посилань-запрошень до бюджету;
- рольова модель доступу в межах бюджету (owner / member);
- CRUD-операції над категоріями з лімітами;
- CRUD-операції над транзакціями;
- автоматичний перерахунок стану бюджету та індикація перевищення ліміту;
- пошук, фільтрація та сортування транзакцій;
- обробка помилкових сценаріїв (невалідний токен запрошення, перевищення прав доступу, некоректні вхідні дані).

## AC-02. Архітектура та структура системи

### Загальний підхід

Використовується тришарова (layered) архітектура з чітким розділенням frontend, backend та бази даних, що взаємодіють через REST API.

### Компоненти системи

**Client (frontend).** Статичні HTML-сторінки, Tailwind CSS, vanilla JavaScript. Відповідає за відображення інтерфейсу та взаємодію з користувачем: рендер форм, виклик API через `fetch`, оновлення DOM. Бізнес-логіка на клієнті відсутня, за винятком базової валідації вводу, яка дублюється на backend.

**Backend (FastAPI).** Складається з трьох внутрішніх шарів:

| Шар | Відповідальність |
|---|---|
| Router | приймання HTTP-запитів, валідація вхідних даних через Pydantic-схеми, виклик відповідного сервісу, серіалізація відповіді |
| Service | бізнес-логіка: перевірка прав доступу в межах бюджету, перерахунок залишку за категорією, обробка запрошень |
| Repository | доступ до даних через SQLAlchemy (CRUD-операції без бізнес-логіки) |

**Database.** PostgreSQL для production-середовища, SQLite для локальної розробки та тестування; обидва підтримуються через SQLAlchemy без зміни коду застосунку.

### Обґрунтування архітектурних рішень

- Поділ Router → Service → Repository забезпечує дотримання принципу єдиної відповідальності та дозволяє тестувати кожен шар незалежно.
- Розділення Pydantic-схем і SQLAlchemy-моделей відокремлює контракт API від структури зберігання даних і запобігає випадковому витоку внутрішніх полів (наприклад, хеша пароля) у відповідь.
- Обрано самостійну реалізацію автентифікації та рольової моделі замість використання Django, оскільки готова адміністративна панель не потрібна, а власна реалізація демонструє архітектурні навички розробника.
- Email-верифікація запрошень виключена з обсягу проєкту: посилання-запрошення містить токен, що перевіряється на стороні сервера; email/SMTP-інтеграція не є критичною для основного сценарію використання.

### Наскрізний потік запиту (приклад: створення транзакції)

Client → `POST /budgets/{id}/transactions` (з JWT у заголовку) → Router валідує тіло запиту → Service перевіряє належність користувача до бюджету та права на запис → Service створює транзакцію через Repository → Service перераховує залишок категорії → Router серіалізує відповідь у форматі JSON → Client оновлює інтерфейс.

## AC-03. Користувацький інтерфейс

### Перелік сторінок

| № | Маршрут | Призначення |
|---|---|---|
| 1 | `/login` | Вхід за email та паролем |
| 2 | `/register` | Реєстрація нового користувача |
| 3 | `/invite/{token}` | Обробка посилання-запрошення до бюджету |
| 4 | `/budgets` | Список бюджетів користувача |
| 5 | `/budgets/{id}` | Деталі бюджету: категорії з лімітами, стан витрат, останні транзакції |
| 6 | `/budgets/{id}/transactions` | Повний список транзакцій із пошуком, фільтрами та сортуванням |
| 7 | `/budgets/{id}/members` | Список учасників бюджету, керування ролями |
| 8 | `/budgets/{id}/categories` | CRUD-операції над категоріями бюджету |

### Навігація

Верхня панель навігації після автентифікації містить: назву застосунку, перемикач поточного бюджету, пункти меню "Транзакції", "Категорії", "Учасники", а також профіль користувача. Неавтентифікованому користувачу доступні лише сторінки `/login` та `/register`.

### Форми введення

| Форма | Поля |
|---|---|
| Реєстрація | email, пароль, підтвердження пароля |
| Логін | email, пароль |
| Створення бюджету | назва, опис (опційно) |
| Категорія | назва, тип (дохід/витрата), ліміт (опційно, лише для витрат) |
| Транзакція | сума, тип, категорія, дата, коментар (опційно) |
| Запрошення | генерація посилання без введення додаткових даних |

Кожна форма проходить валідацію на стороні клієнта з негайним відображенням результату та повторну валідацію на стороні сервера. Помилки відображаються безпосередньо під відповідним полем.

### Відображення даних

Головна сторінка бюджету відображає категорії у вигляді карток із індикатором прогресу (витрачено відносно ліміту) та кольоровим позначенням стану (у межах норми, наближення до ліміту, перевищення). Список транзакцій реалізовано як таблицю з можливістю сортування, фільтрації за категорією, типом, діапазоном дат та автором, а також пошуку за коментарем. Для порожніх наборів даних передбачено інформаційні заглушки із закликом до дії.

### Повідомлення користувачу

Успішні операції супроводжуються короткочасним спливаючим повідомленням. Помилки валідації форми відображаються інлайново під відповідним полем; помилки бізнес-логіки — у вигляді банера або спливаючого повідомлення з описом, зрозумілим користувачу, без розкриття технічних деталей.

### Адаптивність

Інтерфейс адаптується під desktop та mobile за допомогою брейкпоінтів Tailwind CSS: навігаційна панель на мобільних пристроях згортається у випадне меню, таблиця транзакцій перетворюється на список карток, форми відображаються в одну колонку на мобільних та у дві — на десктопних екранах.

## AC-04. Робота з даними

### Перелік сутностей

| Сутність | Опис | Основні поля |
|---|---|---|
| User | обліковий запис користувача | id, email (унікальне), password_hash, created_at |
| Budget | бюджет (особистий або спільний) | id, name, description, created_at |
| BudgetMember | зв'язуюча сутність User–Budget із роллю | id, budget_id, user_id, role (owner/member), joined_at |
| Category | категорія доходів/витрат у межах бюджету | id, budget_id, name, type (income/expense), limit_amount |
| Transaction | фінансова операція | id, budget_id, category_id, user_id, amount, type, txn_date, comment |
| Invite | токен-запрошення до бюджету | id, budget_id, token, created_by, expires_at, used |

### Обмеження цілісності даних

- поле `email` є унікальним та обов'язковим;
- комбінація `budget_id` та `user_id` у таблиці BudgetMember є унікальною;
- значення `amount` перевіряється на додатність на рівні схеми валідації;
- поле `limit_amount` не застосовується до категорій із типом `income`;
- видалення бюджету призводить до каскадного видалення пов'язаних категорій, транзакцій, учасників та запрошень;
- видалення категорії, що вже містить транзакції, реалізується через механізм архівації (soft-delete) для збереження історії операцій.

### Операції над сутностями

| Сутність | Створення | Читання | Оновлення | Видалення |
|---|---|---|---|---|
| Budget | доступно автентифікованому користувачу | список і деталі, доступні учасникам | доступно власнику | доступно власнику |
| BudgetMember | через прийняття запрошення | список учасників бюджету | зміна ролі власником | видалення учасника власником |
| Category | доступно власнику | доступно учасникам | доступно власнику | архівація власником |
| Transaction | доступно учасникам | перегляд, пошук, фільтрація, сортування | автором або власником | автором або власником |
| Invite | доступно власнику | перевірка валідності токена | — | дострокове анулювання власником |

## AC-05. Форми та валідація

### Рівні валідації

1. **Клієнтська валідація** — попередня перевірка вводу в браузері до відправки запиту (обов'язковість полів, формат, довжина). Використовується виключно для покращення взаємодії з користувачем і не є механізмом захисту даних.
2. **Валідація на рівні схеми (Pydantic)** — структурна перевірка вхідних даних щодо типу, формату та довжини, яка виконується автоматично на рівні FastAPI.
3. **Валідація на рівні бізнес-логіки (Service)** — перевірка правил, що залежать від поточного стану системи та не можуть бути виражені на рівні типу поля.

### Правила валідації за формами

| Поле | Правило | Рівень валідації |
|---|---|---|
| email (реєстрація) | коректний формат, обов'язкове поле | клієнт, схема |
| email (реєстрація) | унікальність у системі | сервіс |
| password | мінімум 8 символів | клієнт, схема |
| підтвердження пароля | збіг зі значенням пароля | клієнт |
| email та пароль (логін) | відповідність збереженим обліковим даним | сервіс |
| назва бюджету / категорії | від 1 до 100 символів, обов'язкове поле | клієнт, схема |
| тип категорії/транзакції | значення з переліку income/expense | схема |
| ліміт категорії | додатне значення; недопустиме для типу income | схема, сервіс |
| сума транзакції | додатне число, не більше двох знаків після коми | клієнт, схема |
| дата транзакції | коректна дата, не пізніша за поточну | схема |
| категорія транзакції | наявність та належність до відповідного бюджету | сервіс |
| коментар транзакції | необов'язкове поле, до 255 символів | клієнт, схема |
| токен запрошення | дійсність, термін дії, статус використання | сервіс |

### Відображення результатів валідації

Помилки клієнтської валідації відображаються безпосередньо під відповідним полем форми до моменту відправки запиту. Помилки валідації схеми, що надходять від сервера, розподіляються по відповідних полях форми. Помилки бізнес-логіки, що не прив'язані до конкретного поля, відображаються у вигляді загального повідомлення над формою.

## AC-06. Взаємодія frontend і backend

### Механізм взаємодії

Взаємодія між клієнтською та серверною частинами здійснюється виключно через REST API з передачею даних у форматі JSON. Прямий доступ клієнтської частини до бази даних або серверної логіки відсутній.

### Автентифікація на рівні транспорту

Після успішної автентифікації клієнт отримує JWT-токен доступу, який передається у заголовку `Authorization` кожного наступного запиту до захищених ресурсів. Формування заголовків авторизації централізовано в єдиному клієнтському модулі взаємодії з API.

### Структура API

```
Auth:         POST /auth/register
              POST /auth/login

Budgets:      POST   /budgets
              GET    /budgets
              GET    /budgets/{id}
              PATCH  /budgets/{id}
              DELETE /budgets/{id}
              GET    /budgets/{id}/summary

Invites:      POST /budgets/{id}/invites
              GET  /invites/{token}
              POST /invites/{token}/accept

Members:      GET    /budgets/{id}/members
              PATCH  /budgets/{id}/members/{user_id}
              DELETE /budgets/{id}/members/{user_id}

Categories:   POST   /budgets/{id}/categories
              GET    /budgets/{id}/categories
              PATCH  /budgets/{id}/categories/{cid}
              DELETE /budgets/{id}/categories/{cid}

Transactions: POST   /budgets/{id}/transactions
              GET    /budgets/{id}/transactions
              PATCH  /budgets/{id}/transactions/{tid}
              DELETE /budgets/{id}/transactions/{tid}
```

### Формат обробки помилок

Усі помилки повертаються у єдиному форматі:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "У вас немає прав редагувати цю транзакцію"
  }
}
```

| Код HTTP | Умова виникнення |
|---|---|
| 400 | порушення бізнес-правила |
| 401 | відсутня або недійсна автентифікація |
| 403 | недостатньо прав доступу |
| 404 | ресурс не знайдено |
| 409 | конфлікт даних (дублювання) |
| 422 | помилка валідації вхідних даних |

Клієнтська частина централізовано обробляє відповіді з кодом помилки: повідомлення відображається користувачу у зрозумілій формі; за кодом 401 виконується перенаправлення на сторінку входу; за кодом 422 помилки розподіляються по відповідних полях форми.

### Формат успішної відповіді

Одиничний ресурс повертається безпосередньо у тілі відповіді. Списки ресурсів повертаються з пагінацією:

```json
{
  "items": [ ],
  "total": 42,
  "page": 1,
  "page_size": 20
}
```

### Мережева конфігурація

За умови розміщення клієнтської та серверної частин на різних origin налаштовується `CORSMiddleware` з визначеним дозволеним джерелом. За умови видачі статичних файлів клієнтської частини безпосередньо засобами FastAPI (`StaticFiles`) необхідність у CORS відсутня.
